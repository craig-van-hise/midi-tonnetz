# Product Requirements Prompt (PRP) — 🔘 Pending

## 1. Project Context & Objectives
The MIDI Tonnetz Explorer visualization UI is currently experiencing a state-locking bug. The specific issue occurs when pitch class sets are entered via the Web MIDI API; subsequent attempts to manually toggle these nodes via UI click interactions on the Canvas grid are ignored or overridden. The objective is to debug and refactor the state management logic handling `activeNotes`/`activePitchClasses` so that UI interactions and MIDI events coexist harmoniously, allowing manual canvas clicks to reliably override or toggle the active state of a pitch class regardless of its previous MIDI activation history.

## 2. Technical Decisions & Dependencies
* **State Architecture Refactor:** The root cause is likely either a state closure trap (stale state in the canvas event listeners) or conflicting dual-state sources (e.g., `midiNotes` vs. `clickedNotes` where MIDI takes absolute precedence and fails to clear). 
* **Single Source of Truth (SSOT):** We will implement a unified state handler (e.g., a `Map<number, number>` for active pitch classes acting as a reference counter, or a clean absolute Set). If a user clicks a node, it must invert the current boolean active state of that pitch class (`current_state -> !current_state`). If it forces a note off, it must clear any residual MIDI locks for that specific pitch class.
* **Event Delegation:** Ensure the `onClick` or `onPointerDown` canvas logic inside `TonnetzGrid.tsx` is correctly mapping grid coordinates to the exact pitch class and successfully lifting state to `App.tsx` without being blocked by overlapping absolute-positioned navigation overlays.
